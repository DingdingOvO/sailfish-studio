# 01 - 进程模型与生命周期

[返回 README](../README.md)

## 1. 概述

Sailfish Studio 采用多进程架构，借鉴现代 IDE (VS Code) 和浏览器 (Chrome) 的设计，将 UI 渲染、项目执行和系统管理严格分离。

## 2. 进程定义

### 2.1 主进程 (Main Process)

- **职责**: 窗口创建与管理、系统菜单、托盘、自动更新、全局快捷键、进程间通信 (IPC) 中枢。
- **生命周期**: 应用启动时由 tauri 或浏览器主线程创建，应用退出时销毁。常驻运行，不随项目打开/关闭变化。
- **实现**:
  - 桌面端: Tauri 2.0 的 Rust 后端。
  - Web 端: 浏览器主线程 (与渲染进程共享，但职责通过模块分离)。

### 2.2 渲染进程 (Renderer Process)

- **职责**: 编辑器 UI 渲染，包括积木工具箱、积木编辑区 Canvas、舞台区域、角色列表、属性面板、设置中心、调试控制台等所有可见界面。该进程不执行任何项目逻辑 (积木运算、编译、扩展执行)。
- **生命周期**: 应用启动时创建，退出时销毁。常驻运行，打开/关闭项目不会导致该进程重新加载。
- **实现**:
  - 桌面端: Tauri WebView (单一实例)。
  - Web 端: 浏览器主线程中的 sf-editor 模块。

### 2.3 扩展进程 (Extension Process)

- **职责**: 项目执行环境。每个项目拥有独立的扩展进程，内部加载 sf-vm 的 Wasm 模块，负责编译、运行、扩展加载与执行。扩展进程之间完全隔离，一个项目的崩溃 (包括 Wasm trap) 不会影响其他项目或编辑器 UI。
- **生命周期**: 用户打开项目时创建，关闭项目时销毁。资源严格随进程销毁而释放。
- **实现**:
  - 桌面端: Tauri sidecar 子进程 (推荐) 或 Web Worker (降级)。
  - Web 端: 专用 Web Worker。

## 3. 生命周期管理

### 3.1 扩展进程创建流程

1. 用户在渲染进程中选择打开项目。
2. 渲染进程通过 IPC 向主进程发送 `create_extension_process(project_id, project_path)`。
3. 主进程启动新进程/Worker，传递项目文件路径和会话 Token。
4. 扩展进程初始化 sf-vm，加载项目，通过 IPC 向渲染进程发送 `ready` 信号。
5. 渲染进程更新 UI，开始接收舞台绘制指令和日志。

### 3.2 扩展进程销毁流程

1. 用户关闭项目标签页。
2. 渲染进程通过 IPC 发送 `destroy_extension_process(project_id)`。
3. 扩展进程收到信号后，保存项目状态 (如启用自动保存)、卸载扩展、释放 Wasm 内存。
4. 扩展进程向主进程发送 `terminated`，主进程回收进程资源。

## 4. 进程监控与恢复

- **心跳检测**: 渲染进程每 5 秒向扩展进程发送心跳，若 15 秒无响应，判定为崩溃，提示用户"项目 [名称] 已崩溃，是否尝试恢复?"
- **自动恢复**: 若用户选择恢复，重新创建扩展进程并加载最近的自动保存快照。
- **日志记录**: 崩溃时，扩展进程的日志缓冲区 (环形缓冲) 被写入崩溃报告，供用户反馈或开发者调试。
